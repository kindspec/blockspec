# The editing API's cases

Cases for `blockspec.edit`, the reference implementation's editing API, as
`docs/editing-api.md` designs it. They pin an interface of the reference, not
of the format (`SPEC.md` §2 leaves editor behaviour unspecified), so they
live here and not in `conformance/cases/`. `tests/test_edit_cases.py` runs
them. **Add, do not edit**: a case changed to match the implementation stops
measuring anything.

## Shape

    tests/edit-cases/<group>/<case-name>/
        expect.json     what to assert (required; its presence IS the case)
        input.md        the document before the edit, exact bytes
        source.md       the new block's source, exact bytes (replace, insert)
        output.md       the document after the edit, exact bytes (accepted only)
        WHY.md          prose, ignored by the runner

Every file is exact bytes, decoded as UTF-8 with its line endings kept, so a
CRLF or a bare CR in a fixture is kept. `.gitattributes` exempts this tree
from line-ending normalisation.

## `expect.json`

| field | when | what it asserts |
| --- | --- | --- |
| `op` | always | `"replace"`, `"insert"` or `"delete"` |
| `node` | `replace`, `delete` | the path passed, a JSON array of integers |
| `before`, `after` | optional, `insert` | the path passed as that keyword. Both may be given, to pin `bad-position` |
| `result` | the edit is made | `"output.md"`: the file holding the exact text returned |
| `refusal` | the edit is refused | the one code the refusal carries: an API reason or a `SPEC.md` §9 identifier |
| `controls` | `refusal` is given | ids of accepting cases, as paths relative to `tests/edit-cases/` (`replace/replace-a-paragraph`), on the other side of the line this refusal draws. The runner checks each exists and accepts |

The calls are:

    replace: edit.replace_block(input, node, source)
    insert:  edit.insert_block(input, source, before=..., after=...)
    delete:  edit.delete_block(input, node)

where `input` and `source` are the files' text, and an `insert` with neither
`before` nor `after` passes neither. Exactly one of `result` and `refusal` is
given. A case asserts one refusal, so it is written so that only one
refusal applies, or so that `docs/editing-api.md`'s order decides which.

## Provenance

Written against blockspec `5d7f960` with `docs/editing-api.md` as first
drafted on the branch that adds the API, before any implementation of it
existed. The author worked in an exported directory holding `SPEC.md`,
`docs/` (the adjudications and `editing-api.md`), `conformance/cases/` and
this README, with no `.git`, no `reference/`, no `tests/*.py` and no
`conformance/*.py`, and was given no copy of the conversation that designed
the API. Every fixture was generated by the author's own script and is
written for this tree. The implementation, `reference/blockspec/edit.py`,
was written afterwards and run against the cases with no case changed.

The author's questions led to five clarifications of `editing-api.md`,
none of which changes a case: an empty file's new lines end in LF; a
deleted only block leaves the blank lines after it; the clause about a
blank last line after a delete was unreachable and is gone; a name bound to
a replaced block stays on its replacement; and the unchanged-replacement
comparison ignores line endings. Inserting into an empty file and the
argument type checks are pinned in `tests/test_edit.py` instead, since this
format has no field for a `TypeError`.

One case was added later, with the implementation in hand, so it is not
blind: `refusal/changes-another-block/delete-a-heading-pulls-a-code-block-into-a-list`,
the one input found on which the block-by-block comparison refuses and the
block count does not.
